# 交易面板：重新核对与待机恢复

状态：已按首版范围实现；真实 CTP 只读联调待验收。

配套界面说明：[四种页面状态与文案](UI-SPEC.md)。

## 1. 目标与术语

在交易进程已退出、面板仍显示旧异常时，增加一个「重新核对」按钮。点击后执行一次有时间上限的只读检查；成功后主页面显示「已停止 · 目标合约核对通过」，恢复正常待机布局。

这里的“恢复”是恢复页面对当前事实的正确展示，不是恢复交易、重启旧进程或将旧运行改成正常结束。原运行的异常、成交、轮数和审计记录原样保留。

核对结论只覆盖：本次实际登录的仿真环境及当前配置账户、原运行的全部目标合约、注明时间的查询快照。不宣称整个账户无风险，也不保证之后的账户状态不发生变化。

## 2. 当前代码依据

- `trading_console.py:ConsoleState.current_overview()`：活动锁空闲后读取最后运行；缺少 `summary.json` 就持续显示 `process_abnormal_exit`。现有流程没有保存“进程退出后已重新核对”的结果。
- `live_grid/activity.py:ActivityLock`：区分正在被占用的锁和残留身份记录；不能只看锁文件是否存在或旧 PID 是否存在。
- `trading_console/index.html:renderOverview()/renderContract()`：直接展示旧审计投影中的风险和持仓，需要增加独立的核对结果展示，不能直接覆盖旧合约状态。
- `run.py`：已有环境配置读取与只读连接，但目前是持续打印事件的联调入口，不是一次性结构化核对工具。
- `vendor/vnpy_ctp/vnpy_ctp/gateway/position_query.py`：已有委托、持仓查询完成事件，包含请求编号、结果与错误信息，可复用。
- `docs/adr/0010-process-lock-is-the-only-next-run-gate.md`：旧异常本身不阻止下一次确认启动。本功能不增加持久的“核对通过才准启动”门槛。

## 3. 页面交互

### 3.1 入口

在「进程异常退出」提示旁增加「重新核对」按钮，说明文字为：

> 只查询当前配置账户在本次运行目标合约上的委托和持仓，核对通过后恢复待机页面。

首次适用场景为 `process_abnormal_exit`；核对成功后保留「重新核对」入口。运行中或启动中不提供此操作，继续使用现有运行观察与安全停止流程。

检查对象固定取旧运行的 `run_id`、环境和完整合约列表，不取“启动下一次运行”表单的默认合约，也不只检查当前选中的一个合约。页面显式展示环境和检查对象，例如「广发仿真 · IF2610」。

### 3.2 执行中

- 点击后立即显示「核对中…」与阶段：本地检查 → 连接认证 → 合约确认 → 委托查询 → 持仓查询 → 复核 → 保存结果。
- 同一次核对期间按钮不可重复提交，多个页面共享同一核对任务。
- 临时禁用确认启动和策略保存；浏览器刷新、关闭不影响已开始的核对。再次打开可看到进度或结果。
- 任务异步执行，页面现有 8 秒请求超时不承担整个 CTP 查询过程。
- 建议首版总超时 120 秒，另留最多 10 秒关闭连接；属于待验收的产品默认值，不承诺 CTP 必然在该时间内完成。发送流控按短间隔退避重试，总预算不延长。

### 3.3 成功后的页面

- 主标题：「已停止 · 目标合约核对通过」。
- 明细：「IF2610：多仓 0 手，空仓 0 手，活动委托 0 笔，未知委托 0 笔；核对时间：YYYY-MM-DD HH:mm:ss」。
- 旧红色告警从当前状态区移入「上次运行记录」，保留「上次运行异常退出」及原风险原因，不改写历史合约状态。
- 当前区域不再混用旧“等待风险解除与对账”、旧“最近核对净仓：未核对”或运行中平仓提示。
- 查询结束会关闭临时连接，所以显示「核对连接已关闭」，不能显示“实时已连接”。行情显示为最后记录，不伪造最新价格。
- 保留「启动下一次运行」流程；仍需预览并明确确认启动。检查成功不执行自动启动，也不把确认按钮可用解释成已满足所有实时下单条件。

### 3.4 未通过或未完成

| 情况 | 页面结果 | 是否恢复正常待机提示 |
| --- | --- | --- |
| 任一目标合约有活动委托或未知状态委托 | 核对发现遗留委托，展示合约、数量和状态 | 否，保留风险 |
| 任一目标合约有多仓或空仓 | 核对发现持仓，分别展示多仓、空仓和净仓 | 否，保留风险 |
| 缺配置、认证失败、断线、查询错误或超时 | 核对未完成，显示失败阶段及脱敏原因 | 否，不能按零仓处理 |
| 查询完成但保存结果失败 | 核对结果未保存，恢复未完成 | 否，可重新核对 |
| 核对期间运行身份变化 | 当前运行已变化，刷新到新运行 | 不将旧结果应用到新运行 |
| 账户核对通过，但没有启动预览或策略配置无效 | 已停止，目标合约核对通过；启动配置待核对 | 账户状态恢复，启动配置单独提示 |
| 账户核对通过，但不在策略报价窗口或无新 Tick | 已停止，目标合约核对通过；当前不在报价窗口／行情尚未验证 | 可以待机，不表示当前能够报价 |

失败后不自动撤单、平仓或重新启动；用户处理实际问题后可再次点击核对。一次失败不能继续显示为本次成功，之前成功的记录只能放在历史中。

## 4. 检查内容和判定规则

### 4.1 必须完成的账户核对

1. **对象与活动状态**：请求的运行仍为当前异常记录，审计中的环境与合约完整且一致；不存在活动交易或启动任务。锁无法确定、身份记录损坏时不能猜测为空闲。
2. **有效配置与依赖**：检查该环境的实际进程配置；缺失时只返回变量名，不返回凭证。使用项目内 CTP 依赖及匹配的原生库；缺少结构化查询契约则失败。
3. **交易连接**：完成认证、登录及查询所需准备。通过当前配置登录哪个账户，结论就只属于哪个账户；不自动切到 `first` 或 `7x24`。
4. **目标合约可识别**：原运行每个目标合约的元数据都已获得。缺少合约元数据时不可利用被网关过滤后的空持仓集合宣称零仓。
5. **委托查询**：等待本次请求编号对应的完成事件。必须成功结束、无任何查询错误或不可解析的目标委托；逐合约区分终态、活动和未知状态，去重后计数。历史已成交或已撤销委托可以存在，不要求“当日委托总数为 0”。
6. **持仓查询**：委托查询完成后再串行查询持仓，只接受本次请求的完整结果。分别计算多仓、空仓和总持仓；要求每个目标合约多仓 = 0 且空仓 = 0。多 1 手、空 1 手的净仓为 0，不算通过。
7. **查询一致性复核**：完成持仓查询后再次查询目标委托；两轮委托均无活动/未知委托，并且期间未出现目标合约新报单、成交或断线。发生变化即判定本次快照不稳定，需要重新核对，不沿用先前零仓。
8. **落盘与收尾**：再次核对运行身份没有变化、结果可完整保存、临时进程已经关闭，再发布完成结果并释放互斥资源。

空结果只有在“正确请求编号 + 明确完成 + 全程无查询错误 + 目标合约可识别”同时满足时，才是零仓或零活动委托证据。单纯等待一段时间没有事件、只有请求受理、读取旧缓存、仅查询到其他合约，均不能通过。

CTP 委托与持仓查询并非跨请求原子快照。上述串行复核与回报检测用于发现期间变化；外部交易软件、其他机器及查询结束后的操作不受本机锁约束，因此页面始终注明“截至核对时间”，实际启动仍执行原有实时核对。

### 4.2 同时展示的启动检查

复用现有配置解析、环境检查与报价窗口计算，展示：

- 当前选中/已预览策略是否合法、合约列表与配置指纹是否变化；没有预览就写“待预览”，不自动选列表第一个文件。
- 启动表单环境是否与本次账户检查环境一致；不一致时明确提示此次结果不覆盖所选环境。
- 当前是否处在所选策略的报价窗口。此处名称固定为“策略报价窗口”，不把配置时间当作交易所营业日历。
- 行情连接、Tick 新鲜度、稳定盘口等注明实际已验证的范围。首版账户核对不要求行情成功，也不为等新 Tick 而延长任务。

账户风险核对与下一次启动准备分别显示。配置预览成功只说明本地参数合法；资金、实际登录、盘口、涨跌停、稳定行情与下单资格等仍以交易入口的现有运行门槛为准。

### 4.3 闭市行为

按钮不按开闭市时间禁用。能登录交易前置并完成查询，就允许核对通过；查询服务不可用时显示“当前未能完成账户核对，请在前置恢复后重试”，保留未确认状态。不能以“闭市”推定零仓，也不能以没有行情 Tick 判定查仓失败。

## 5. 结果范围、历史账户与时效

现有旧运行身份只记录环境、合约等，不包含可验证的账户绑定。因此首版明确采用“当前配置账户核对”语义：

- 本次结果绑定当前控制服务配置上下文、旧运行编号、环境和原运行全部合约。新运行或环境切换不能继承它。
- 老记录核对成功后可以将当前页面恢复待机，但保留说明：“原运行账户一致性未记录，本次结果仅覆盖当前配置账户。”不宣称旧运行当时无仓或旧账户风险已解除。
- 控制服务生命周期内使用不含凭证的随机上下文编号关联结果；敏感账户信息只在进程内用于比较，不写入审计或接口。刷新页面不丢失结论。
- 控制服务重启后仍能展示已保存的核对历史，但显示「已停止 · 待重新核对」，不把旧核对冒充本次配置账户的最新验证，也不只因旧 `summary.json` 缺失重新宣告刚发生异常。
- 不引入定时后台核对、实时持仓看护或额外的固定有效期。所有完成结果带绝对核对时间及“查询快照”；再次核对失败必须显式显示最新失败。

若后续要求“证明旧运行账户已完全解除风险”，需另行为未来运行记录可验证且脱敏的账户绑定；旧记录缺少的证明不能事后编造。本功能首版不以此阻塞当前账户的可用检查。

## 6. 最小实现方案

### 6.1 接口与任务

- 新增 `POST /api/run/recheck`，请求只含 `run_id`。环境、合约和审计路径由服务端解析，不能让浏览器提交任意路径、凭证或任意查询范围。
- 复用现有 Host、Origin、JSON 和控制台令牌校验；受理返回 202 与 `check_id`。相同运行已有核对时返回已有任务，身份冲突返回 409。
- 复用 `GET /api/run/current` 的轮询，在原运行快照之外增加 `recheck` 结果和明确的当前展示状态；无需新增 WebSocket、任务队列或第二个轮询接口。
- 核对任务结果至少包含：`check_id`、`run_id`、环境、目标合约、配置上下文编号、开始/结束时间、查询交易日、阶段、结果、每合约多空仓及活动/未知委托数、查询编号、脱敏错误。未确认的数值是 `null`，不是 0。
- 采用一个短生命周期只读子进程；控制服务负责受理、观察、超时与结果展示。子进程不创建 `LiveGridSession`，不使用会自动撤遗留单的交易 adapter，也不调用 `run_live_grid.py`。
- 复用 `run.load_settings()`、`activate_ctp_native_libs()`、现有网关及其查询完成事件。使用目标合约查询模式，避免为了 IF2610 等待全市场合约加载；处理好后台定时查询与手工请求的串行关系。
- 首版只依赖现有库和 Python 标准库。只读工具只开放连接、查询、关闭能力；任何报单、撤单路径不得进入该子进程。

### 6.2 启动、核对及退出竞态

仅禁用前端按钮或使用控制服务的线程锁无法阻止命令行同时启动。

在 `live_grid/activity.py` 中增补一个简短的跨进程操作锁，统一由核对进程及已确认交易入口使用：交易启动先取得操作锁，再取得既有活动运行锁并写入身份，随后释放操作锁；核对先取得操作锁并检查活动运行锁，持有操作锁直到查询、落盘和进程关闭完成。两条路径锁顺序一致。

该锁只是避免 CTP 核对、原生库准备与新运行并发，空闲后立即释放；原 `.active-run.lock` 的活动交易语义与最后运行记录不变。查询进程不得伪装成活动交易或覆盖旧运行身份。

核对期间的启动请求明确返回忙碌，不排队自动交易。交易启动先取得锁时，核对请求拒绝。核对进程自身持锁，避免控制服务崩溃后遗留子进程与新交易并发。

子进程超时先尝试正常关闭，关闭预算耗尽时只终止本次确切的只读子进程，绝不按旧 PID 操作交易进程。异常退出不发布通过；已写入但未最终确认的结果保持未完成。控制服务恢复时根据任务记录和锁识别中断状态，不把历史 `checking` 永久挂住。

### 6.3 持久化与投影

在对应 `audit/<run>/rechecks/<check_id>.json` 原子保存独立核对记录；首版文件存储即可。记录中不写账号、密码、认证码、前置地址或未经筛选的原始 CTP 报文。

按同一运行的最新一次核对记录展示，不能在最新失败后回退到较早的成功。缺文件、半文件、非法字段或审计写入失败都不能被解释成通过。

不创建伪造的 `summary.json`；不覆盖 `events.jsonl`、历史状态、原轮数和持仓；不删除活动锁记录来消除告警。现有离线报告仍按真实结束摘要判断是否可生成，核对成功不会让异常运行获得虚假的“正常结束报告”。

建议改动点：

| 文件 | 责任 |
| --- | --- |
| `trading_console.py` | 核对接口、子进程生命周期、结果读取及当前展示状态 |
| `trading_console/index.html` | 按钮、阶段进度、结果、正常待机与历史异常展示 |
| 新增 `live_grid/account_recheck.py` | 一次性只读查询、请求关联、总超时、结果汇总；可由 `python -m` 启动，无需再加独立入口文件 |
| `live_grid/activity.py`、`run_live_grid.py` | 启动和核对的跨进程互斥，保留原活动锁语义 |
| `tests/test_trading_console.py`、`tests/test_activity.py`、`tests/test_console_ui.cjs` 及必要的核对测试 | 接口、并发与展示回归，以及只读查询成功/失败场景 |
| `CONTEXT.md`、`docs/live-grid-runtime.md`、相关 ADR | 实现后同步“核对恢复”的语义、限制和临时互斥规则 |

现有网关完成事件主要透传最后一条响应的错误。实施时必须验证“前面响应报错、最后响应成功”等情况是否会丢失错误；若会，需在项目内网关按请求保留错误并使完成事件失败，补一项针对性回归。该必要补丁不得写入 site-packages，也不借机重构交易状态机。

## 7. 验收标准

1. 原 IF2610 异常案例：无活动交易，完整查询证实目标合约双向零仓且无活动/未知委托；一次点击后主页面恢复待机，展示核对时间，原异常详情仍可查看。
2. 当前表单默认选中苹果合约或其他环境：点击 IF2610 旧告警的核对仍检查旧运行的 IF2610 和原环境，不能因错误默认项通过。
3. 存在多仓、空仓、双向等量仓、活动委托、未知委托任一种情况：均不通过；终态历史委托不阻止通过。
4. 无回调、错误请求编号、部分结果、缺合约元数据、流控耗尽、途中断线、查询超时、早期响应错误：均不按零值通过，给出失败阶段。
5. 多合约运行：只要一个目标合约未通过，整体不能恢复“全部核对通过”；每个合约各自列出事实。
6. 核对期间出现目标委托或成交，或者两轮委托查询不同：结果为状态变化、需重新核对，不能沿用旧零仓。
7. 运行中误调用、两个页面同时点击、命令行和页面并发启动、控制服务重启：没有并行交易与核对，没有旧结果覆盖新运行，没有永久卡住的检查任务。
8. 闭市但交易前置可查询：能够通过；行情断开或没有 Tick 不影响已成功完成的账户查询。前置不可用则明确未完成。
9. 浏览器刷新后结果保留；控制服务重启后显示历史核对时间及待重新核对，不能假定本次账户身份相同。
10. 配置有误、策略无预览、不在报价窗口：对应启动检查准确显示，不能将账户核对成功写成“实时下单条件全部满足”。
11. 成功、失败、超时及退出等路径均验证 `send_order`、`cancel_order` 调用数为 0；临时连接关闭后无残留核对进程。
12. 文件权限不足、记录损坏与写入中断：页面不虚报恢复成功；原审计与已有用户配置不受影响。

先完成离线查询契约、并发和页面测试，再在可用的仿真前置进行一次有界只读联调，核实真实查询完成、结果落盘、界面恢复与进程退出。离线测试通过不能代替真实连接验收，真实联调不包含报单、撤单或平仓。

## 8. 首版范围

只交付旧异常场景的主动核对、结果保存与待机展示，不增加数据库、自动监控、自动交易、订单处置、全账户风险认证或复杂配置中心。方案本身不修改运行中的服务、交易逻辑或现有策略参数。
